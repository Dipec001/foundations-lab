## The big idea

A container is a normal Linux process with three things added. There's no container object in the kernel.

1. **Own root filesystem** (chroot or pivot_root): its own `/`, so it brings its own programs and libraries.
2. **Namespaces:** what it can see (processes, mounts, network, hostname).
3. **cgroups:** what it can use (memory, CPU, number of processes).

A Linux OS = the kernel + the userland. The container brings only the userland, as files. It always shares the host's kernel, which is why `uname -r` inside Alpine printed the VM's `7.0.0-42-generic`. A VM has its own kernel; that's why containers start in milliseconds.

The Docker `alpine` image is the same 3 MB tarball I unpacked: `FROM scratch` plus `ADD alpine-minirootfs-...tar.gz /`.

## cgroups: what I worked out

Every process is in exactly one cgroup. A group is a directory, and its files hold the members and the limits.

| Path | View from | Answers | Used for |
|---|---|---|---|
| `/proc/<PID>/cgroup` | the process | Which group am I in? | reading |
| `/sys/fs/cgroup/<group>/` | the group | Who is in me, what are my limits? | reading and changing |

Files inside a group directory:

| File | Holds | You write |
|---|---|---|
| `cgroup.procs` | the PIDs in this group | a PID, to move that process in |
| `memory.max` | the memory limit | e.g. `50M` |
| `cpu.max` | the CPU limit | e.g. `20000 100000` (20% of one CPU) |

- An empty group enforces nothing. Limits only apply once a PID is in `cgroup.procs`.
- Children inherit their parent's group by default. That's why each `cat` showed up in my session's list, then vanished.
- Writing a PID into another group's `cgroup.procs` moves it. It leaves the old group.
- The root of `/sys/fs/cgroup` has no `memory.max`. You make your own group to set limits.
- Directories are groups, files are settings. systemd names: **slice** = a group of groups, **scope** = processes started outside systemd, **service** = a system service.

The tree I traced:

- `system.slice/ssh.service` holds sshd (PID 932), alone.
- `user.slice/user-1000.slice/session-3.scope` holds my login: `sshd-session [priv]` (1228), `sshd-session` (1275), `bash` (1276). systemd moved 1228 there when I logged in.

## The commands that worked

Each one with the reason it's there. Run in the Multipass VM, inside `~/tiny`, unless it says otherwise.

**0. Grow the VM disk** (on the Mac, VM stopped). kind needs room; a disk can only grow.

```bash
multipass stop snappy-monarch
multipass set local.snappy-monarch.disk=20G
multipass start snappy-monarch
df -h /    # disk free, human-readable, root filesystem only
```

**1. Look at cgroups from both sides.**

```bash
cat /proc/self/cgroup        # which group is this process in?
echo $$                      # PID of my shell
cat /sys/fs/cgroup/user.slice/user-1000.slice/session-3.scope/cgroup.procs
ps -o pid,ppid,cmd -p 1228,1275,1276   # who are these PIDs, and who is their parent?
cat /proc/932/cgroup         # sshd lives in system.slice/ssh.service
ls -d /sys/fs/cgroup/*/      # only the groups (directories)
```

**2. Get a root filesystem.** A container needs its own `/`; a rootfs is just an ordinary directory.

```bash
mkdir -p ~/tiny/rootfs && cd ~/tiny
curl -s https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/aarch64/ \
  | grep -o 'alpine-minirootfs-[0-9.]*-aarch64.tar.gz' | sort -u | tail -1
curl -LO https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/aarch64/alpine-minirootfs-3.24.4-aarch64.tar.gz
sudo tar -xzf alpine-minirootfs-3.24.4-aarch64.tar.gz -C rootfs
ls -ld rootfs/bin            # owner must be root
```

`sudo` because a real system's files must belong to root, and files belong to whoever creates them.

**3. Change the process's root with chroot.** The command path is read after the root changes, so it's `/bin/sh`, not `./rootfs/bin/sh`.

```bash
sudo chroot ./rootfs/ /bin/sh        # or: /bin/busybox sh
# inside:
cat /etc/os-release   # Alpine
uname -r              # the VM's kernel: containers share the host kernel
ls -l /bin/sh         # -> /bin/busybox
```

**4. Mount /proc by hand (inside the chroot).** `/proc` is generated by the kernel when read; from a tarball it's an empty folder.

```bash
mount -t proc proc /proc   # type, label (no real device), where
ps                         # now shows EVERY VM process: chroot is not process isolation
```

After `exit`, the mount stayed attached to `~/tiny/rootfs/proc` on the VM. Remove it with `sudo umount ./rootfs/proc`.

**5. Add a PID namespace.** My shell becomes PID 1 and sees nothing else.

```bash
sudo unshare --pid --fork --mount-proc=./rootfs/proc chroot ./rootfs/ /bin/sh
# inside:
ps    # 1 /bin/sh, then ps itself
```

- `--pid`: new PID namespace, but only for children, never for `unshare` itself.
- `--fork`: start a child so it lands in the new namespace as PID 1.
- `--mount-proc=./rootfs/proc`: fresh proc for the new namespace. It implies `--mount`, so the mount stays private. The path is the outside name, because `unshare` runs before `chroot`.
- `chroot` does an exec: it becomes `/bin/sh`, keeping PID 1.

## Mistakes and the rule each one taught

| What I typed | What happened | The rule |
|---|---|---|
| `tar -xfzC file` | `zC: Cannot open` | A flag that takes a value grabs what comes right after it. Put it last in a bundle: `-xzf file`. |
| `--file=ARCHIVE` | `ARCHIVE: Cannot open` | Capitals in help text are placeholders for your own value. |
| `-C=rootfs` | looked for a folder named `=rootfs` | Short flag + space (`-C rootfs`); long flag + equals (`--directory=rootfs`). |
| `-C=/rootfs` | no such directory | A leading `/` starts at the top of the system. No `/` = relative to where you are. |
| `tar` with no `-C` | files spilled into `~/tiny` | Without `-C`, tar extracts wherever you are. |
| `rm -rf vae` | nothing, silently | `-f` hides typos. Use `-r` alone, preview with `echo` first. |
| tar into rootfs, no sudo | `Cannot utime: Operation not permitted` | A normal user can't change root's files. |
| `chroot ./rootfs/ ./rootfs/bin/sh` | `No such file` | The command path is read after the root changes. |
| `mount -tf proc ...` | dry run, usage error | Same bundle rule as tar: `-t` takes the next thing. |
| `--mount-proc` with no dir | `ps` empty inside | It mounted on the VM's `/proc`, then chroot moved the shell away. Mounted, but not where the process looks. |

**Two corrections to remember for interviews:**

- The systemd I saw was the VM's PID 1, not the Mac's. The Mac has its own kernel; nothing in the VM can see it.
- A process can never move itself into a new PID namespace. Only its children land there. That's why `--fork` exists, and why `unshare` stays outside.

**Open question from Friday:** which namespace kept the proc mount private in step 5, and why did it leak in step 4?

<details><summary>Answer (try it cold first)</summary>

The **mount namespace**. In step 5, `--mount-proc` implies `--mount`, so `unshare` made a new mount namespace and the proc mount only existed inside it. When the namespace's last process exited, the mount went away with it. In step 4 there was no new mount namespace: `chroot` changes only what `/` means for that process, so `mount` inside it added the mount to the VM's own mount table, and it stayed there after `exit`.

</details>
